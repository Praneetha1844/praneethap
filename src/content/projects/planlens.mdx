> **Status:** implementation complete, benchmarks not yet published. This page describes the design intent and scope. The repository README is the source of truth for the exact behaviour.

## Problem

Query tuning is often done by trial and error: add an index, run the query again, hope. PostgreSQL already tells you what it does through `EXPLAIN`, but reading a large plan and turning it into a decision takes practice.

Planlens is a query-plan analyser and index advisor that tries to make that reading systematic.

## Approach

1. **Read** the plan PostgreSQL produces for a query.
2. **Explain** where the work happens: which operations dominate and which scans touch many rows to return few.
3. **Suggest** indexes that could change the plan, with the reasoning.

The goal is advice a person can check, not a black box: each suggestion points at the part of the plan that motivated it.

## Design considerations

- **Plans are evidence.** Conclusions come from the plan, not from guesses about the schema.
- **Suggestions are hypotheses.** An index that looks helpful can be ignored by the planner, slow down writes or bloat storage. The tool presents candidates to be tested, not changes to apply blindly.
- **Reproducible comparison.** Plans and timings are only meaningful when the data and the settings are described, so the project favours scripted, repeatable comparisons over one-off screenshots.

## Why it matters

Relational design, SQL and query optimisation are core skills for data engineering. This project is where I practise them deliberately.

## Limitations

- Suggestions are advisory and are not validated against every workload.
- No benchmark results are published yet. Any speed-up claim will appear only with the data, the settings and the commands needed to reproduce it.

## Roadmap

- Publish a reproducible benchmark with a generated dataset.
- Show before-and-after plans for each suggestion.
- Account for write cost and index size in the advice.
